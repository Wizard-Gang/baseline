# baseline

`baseline` is the WizardGang change-management reference implementation. It contains governance, executable repository contracts, CI, provider policy, and a release path. It intentionally contains no application or product code. Its one code grant is `platform/`, which may hold shared edge code that consuming repositories vendor; baseline has no deployment target and never deploys a Worker itself.

The contract gate is `npm ci && npm run check && npm run audit:dependencies`. A controlled change then requires an exact-head pull request, current required checks, a squash merge, and post-merge verification. Successful exact-current-main CI cuts or verifies an annotated semantic tag and explicitly dispatches Release at that tag; the source and assets must reproduce. [Change management](docs/CHANGE-MANAGEMENT.md), [release management](docs/RELEASE-MANAGEMENT.md), and [ownership](docs/OWNERSHIP.md) define the operating sequence.

[The control map](docs/CONTROL-MAP.md) lists every committed guard, its authority, and the evidence needed to verify it. Repository auto-merge is available for an individually configured PR; required checks, squash-only merge, and the controlled record still govern that PR.

`config/phase.json` keeps application development disabled and declares the `platform` grant: path `platform/`, shared edge code only. The repository contract accepts `platform/` only under that exact grant and keeps rejecting the application paths `src`, `app`, `apps`, `game`, `pages`, `public`, `workers` and `functions`. The repository can become an application seed only after the contract has passed local tests and a live provider exercise covering a PR, merge, tag, immutable GitHub Release, asset digest, and provenance attestation. Until that proof exists, changes should improve this reference implementation only.

## Authority

1. Git source, test assertions, workflow files, and committed configuration define executable contracts.
2. `config/github-repository-settings.json` is the desired GitHub provider state; live readback is required to claim convergence.
   `config/cloudflare.json` is the desired Cloudflare state for the four `wizardgang.ai` Workers. `scripts/cloudflare-desired-state.mjs` keeps it exact and closed during `npm run check`; it holds names only, never an account ID, binding ID or secret value, and claims intent, not live convergence. `npm run verify:cloudflare` is the separate read-only live comparison.
   `config/secrets.json` is the WizardGang secret registry: every secret, plain variable and derived key, with its kind (`secret`, `variable` or `derived`), home (a Worker, the Secrets Store, a GitHub environment or the owner's keychain), consumers, provider, console credential (`wg-<provider>-<purpose>`) and purpose. `scripts/secret-registry.mjs` keeps it closed during `npm run check`. Secrets are named `<PROVIDER>_<PURPOSE>_<KIND>` with KIND `TOKEN`, `CLIENT_SECRET`, `WEBHOOK_SECRET`, `PRIVATE_KEY` or `KEY`. Shared platform secrets carry `WG_` and live only in the Secrets Store, and wrangler's `CLOUDFLARE_API_TOKEN` and `CLOUDFLARE_ACCOUNT_ID` live only in GitHub environments. Client, tenant, app and account IDs, issuers, URLs and certificates are variables, never secrets. There are no repository-level GitHub secrets, no duplicate name in one home and one console credential per name. Every derived key names `WG_SESSION_KEY` as its source. The one recorded exception is the demo's `wg-cloudflare-demo` deploy token, which ends with the demo's Phase 4 D1 move. Each Worker's `secrets` and the Secrets Store list in `config/cloudflare.json` must equal the registry's. The registry is the target, not live state; it holds names only, never a value or an ID.
3. Current-state policy documents describe responsibilities and intent.
4. Git first-parent history, pull requests, workflow runs, annotated tags, Releases, and attestations are the historical evidence. The repository does not keep a parallel release ledger.

The Node and npm versions are pinned by `.node-version` and `package.json`. `package.json` owns the release version. Any future application versioning authority must be introduced by a controlled change before product code is added.

## Start here

```sh
npm ci
npm run check
npm run audit:dependencies
```

`npm run check` needs no GitHub credential. Live provider checks use `GH_ADMIN_TOKEN`, or `GH_TOKEN` when it has the required permissions. `npm run verify:github-settings` only reads repository metadata, immutable Releases, and rulesets; `npm run apply:github-settings` changes only the committed merge settings, immutable Releases, and rulesets, then independently re-reads them. Keep the token in process or provider secret state and never print it.

[`platform/wg-edge/`](platform/wg-edge/README.md) is the shared Worker shell: host guard, TLS rule, `/version.json`, `/health.json`, `robots.txt`, the fail-closed `/admin/*` operator gate, security headers, Accept-driven 404s, a redacting error boundary, structured logs, and D1/R2 helpers and a TTL sweeper scoped by `WG_APP`. It is dependency-free ESM with a hand-written `index.d.ts`, and `npm run check` tests it on Node with a `node:sqlite` D1 fake and an in-memory R2 fake. Baseline ships only a Worker config template and deploys nothing.

[`platform/migrations/`](platform/migrations/0001_universal.sql) is the schema of the shared `wizardgang` D1 database, and baseline is its only DDL owner. `0001_universal.sql` creates `records` and `events` as STRICT tables with JSON-text bodies, integer-millisecond times and indexes for owner, expiry and app-time lookups. The wg-edge D1 fake is built from these files, so every helper test runs against the real schema. The repository contract allows SQL only as `platform/migrations/NNNN_name.sql`, numbered contiguously from `0001`, with each file SHA-256 pinned in `platform/migrations/pins.json` in the commit that adds it. `npm run check:patch` fails a patch that re-pins or drops a merged migration. Consumers ship no DDL. The owner creates the database and applies migrations from [the Cloudflare runbook](docs/CLOUDFLARE-RUNBOOK.md); no baseline command or workflow touches live D1.

[`platform/conformance/`](platform/conformance/README.md) keeps consumers from drifting. A consumer vendors `platform/` verbatim from a merged baseline commit and commits the lock that `npm run vendor:lock -- <commit>` prints as `platform/vendor.lock.json`: the source commit and a SHA-256 for every file. `node platform/conformance/cli.mjs pin` then fails on any edited, missing, unpinned or non-regular file. `node platform/conformance/cli.mjs wrangler --worker <label>` checks the consumer's `wrangler.jsonc` against its entry in `config/cloudflare.json`, mirrored into the vendored `desired.mjs`. The checks cover a single top-level Worker with no `env` or `account_id`, the name and `WG_APP` identity, and exactly one custom domain (plus `www` only on `wizardgang`). They also require the shared compatibility settings, with workers.dev and preview URLs off and observability on. Bindings are limited to D1 and R2 `wizardgang` as `WG_DB` and `WG_R2`, the declared Durable Objects and crons, and Secrets Store `WG_OPS_TOKEN` and `WG_SESSION_KEY` only. [`platform/wrangler.template.jsonc`](platform/wrangler.template.jsonc) is the conforming shape. Baseline's own `platform/` carries no lock.

[`.github/workflows/deploy-worker.yml`](platform/deploy/README.md) is the one reusable tag-to-production deploy for every Worker, and baseline only hosts it. Its sole trigger is `workflow_call` from a consumer. A secret-free `verify` job binds the annotated `vX.Y.Z` tag to `package.json` and the expected commit on `main`, then runs `npm ci`, `npm run check`, the vendored `pin` and the `wrangler` conformance check. A `deploy` job bound to the caller's `production` environment then runs the caller's locked `wrangler deploy` with resource provisioning off, so it can never create D1 `wizardgang`. It confirms that the new version serves 100% of traffic and polls `https://<host>/version.json` until the tag's version and commit appear. The repository contract keeps baseline itself from ever deploying: no other trigger, no caller workflow, no wrangler dependency, config or script.

`npm run verify:cloudflare` compares live Cloudflare with `config/cloudflare.json`. It needs runtime `CLOUDFLARE_API_TOKEN` (the read-only audit token) and `CLOUDFLARE_ACCOUNT_ID`, issues GET requests only, never reads secret values and never prints the token. It lists missing, unexpected and mismatched items and exits 0 when converged, 1 on drift, 2 when credentials are missing or malformed, 3 when read access is denied and 4 for an invalid authority or any other API failure. It is owner-run: neither `npm run check` nor any workflow calls it, and its tests use recorded API fixtures.

`npm run discover:cloudflare-token-targets` and `npm run rotate:cloudflare-token` take their targets only from `config/secrets.json`: its `github-environment` secrets and variables, and its exceptions, in the repositories declared in `config/cloudflare.json`; no owner or repository is listed beyond it. Both read names and `updatedAt` only, never a value, through an authenticated `gh`. Discovery is read-only. It prints one line per registry entry (repository, environment, kind, name, console credential, `updatedAt`) and reports as drift anything outside the registry: a repository-level secret or variable, another environment, an unregistered name, a missing environment or entry, and an entry stored as the other kind (`CLOUDFLARE_ACCOUNT_ID` held as a secret today). It exits 0 ready, 1 drift, 2 usage or missing `gh` credentials, 3 denied reads and 4 an invalid authority. Rotation requires `--credential <console name>`: `wg-cloudflare-deploy` writes the `production` `CLOUDFLARE_API_TOKEN` of WizardGang, SharkTank and Hexframe, and `wg-cloudflare-demo` writes only the demo's, through the registry exception. An unknown credential, or one with no GitHub-environment Cloudflare target, exits 2 before any read or write. Rotation prints the plan and drift and changes nothing unless given `--apply`. It then reads the new token from piped stdin only (never a terminal or an argument), checks that Cloudflare reports it active, writes each mapped target with `gh secret set` over stdin, and re-reads `updatedAt` after every write. A failed write, a failed re-read or an unchanged `updatedAt` fails the run with exit 1. The value never appears in an argument, the environment or the output. Both are owner-run: the repository contract keeps them out of `npm run check`, every other package script and every workflow, and `npm run check` tests them against a stubbed `gh`.

[The Cloudflare runbook](docs/CLOUDFLARE-RUNBOOK.md) is the owner's only path for provider changes. It covers the Phase 1 orphan deletes, the Phase 3 provisioning (the read-only audit token, D1 `wizardgang` and its migration, R2 `wizardgang` and its lifecycle rules, the Secrets Store values and the scoped deploy token), the deploy rollback and the gated later retirements. Every step has a fresh read-only precondition, usually `npm run verify:cloudflare`, plus the exact owner-run command, a read-back and a rollback. It holds no token value or account ID, and no agent or workflow runs it. `npm run check` keeps its links, npm script names, resource names and lifecycle rules current against `package.json`, `config/cloudflare.json` and the recorded 2026-10-03 inventory.
